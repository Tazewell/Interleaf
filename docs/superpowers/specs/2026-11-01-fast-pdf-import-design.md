# PDF 导入先可检索，版面解析后台继续

用户要求：在 `dev` 开发；参考 Zotero；导入后先能阅读和搜索，完整精细解析在后台继续；同时考虑一次导入多篇。

## 已测量的问题

Windows x64、i9-13900H，当前安装包处理 Oze 测试论文（13 页、1.14 MB）：完整布局 26.5–29.5 秒，其中推理 24.1–26.9 秒；同一处理器仅提取文字 0.37–0.38 秒。不是 Zotero 运行速度测试。现有全文索引 worker 跳过正在排队或运行布局的论文，库搜索也只读取布局结果，因此轻量能力被重型工作挡住。

## 决定

- 保留独立、单线程的全文索引队列，让论文在 layout queued/running 时也能提取原生文字；无已有索引的新导入优先于布局完成后的索引升级。成功后立即处理下一篇，空队列或冲突时等待，避免忙循环。
- 论文布局在该文档初次轻量索引 queued/running 时等待它；轻量索引失败仍允许布局继续，失败任务不无限重试。其它文档的轻量索引与当前布局可同时进行。
- 保留现有单个布局 worker、模型、分辨率、精度、全页覆盖、翻译设置、数据目录和安装包。此任务不加入 GPU、模型转换或额外并发推理。
- 全库搜索、命令行文本读取优先使用已完成布局；布局尚不可用时，读取已保存的轻量 corpus，不在搜索请求里同步解析。轻量块使用 corpus ID 与页定位，不伪造精细布局块或声明布局完成。
- `Processing.textIndex` 是响应时动态计算的可选字段：`{status: queued|running|ready|partial|unavailable|failed, totalPages: number, searchablePages: number}`；只对 PDF 返回。已有可用 corpus 优先于正在升级的 job。没有文字的扫描页不得显示全文可搜索。两条 worker 不同时重写 Processing body。
- 界面区分建立索引、可搜索、部分可搜索、无文字与失败；精细工作明确显示为后台版面解析。现有翻译进度、重试、离线状态继续工作。
- 解析发布与 corpus 提交必须一致：捕获 parser generation，哈希/提字放在发布锁外；提交前短读锁验证 generation 并提交 SQLite。若来源变化则重排，不将正常发布竞态记为永久失败。删除/取消不得复活任务或残留可检索内容。
- 轻量文字只提前开放阅读与搜索；自动概要仍明确等待论文精细版面解析结束，避免先基于快速索引付费生成、版面升级后再次付费。现有翻译启停与手动翻译设置不变。

## 验收

多个 PDF 导入时，即使第一篇布局被阻塞，后续论文也能完成轻量索引并由实际库搜索 API 找到。精细布局发布后自动升级索引；索引失败不阻止布局；扫描件不虚报搜索能力；重启、删除和发布竞态有回归测试。使用临时库和仓库 fixture 验证，不读取真实用户 API 设置或文档。依赖不变，不推送或发布版本。
